# Market Price Series and Corporate Action Policy

**Project:** AI Quantitative Trading & Decision Intelligence System\
**Document status:** Revised policy draft\
**Last updated:** 24 October 2026\
**Primary market-data source:** Yahoo Finance, accessed through
`yfinance`\
**Initial development asset:** Lloyds Banking Group (`LLOY.L`), London
Stock Exchange\
**Portfolio simulation currency:** GBP

## 1. Purpose and scope

This policy defines how historical market data is acquired, checked,
interpreted and used in forecasting, portfolio simulation and
backtesting. Its purpose is to keep price series, corporate actions,
feature engineering, target generation and simulated execution
internally consistent.

The initial development asset is Lloyds Banking Group (`LLOY.L`). The
system is intended to support other eligible assets when selected by the
user and when the required data and validation checks pass. The policy
is therefore reusable; asset-specific findings must be documented
separately.

This document defines methodological requirements. It does not certify
that the current `LLOY.L` dataset has been downloaded, fully reconciled
or approved for trading simulation. Those activities require recorded
execution evidence.

## 2. Approved market-data source

Yahoo Finance, accessed through the Python `yfinance` library, is the
project's approved market-data source for the current implementation. No
Tiingo integration is part of the approved acquisition workflow.

The active asset configuration is expected to specify the ticker,
exchange, country, currency, data provider, date range and interval. The
initial configuration uses:

-   **Ticker:** `LLOY.L`
-   **Exchange:** London Stock Exchange (`LSE`)
-   **Country:** United Kingdom
-   **Currency:** GBP
-   **Provider:** `yfinance`
-   **Interval:** daily
-   **Configured start date:** 1 January 2015

The configured end date is an acquisition parameter, not proof that the
last date has valid observations. The acquisition process must establish
the actual latest available session from the downloaded data. Market
holidays, provider delays and the end-date convention can mean that the
final observation precedes the configured end date.

The project must record the acquisition parameters, retrieval time,
library version, file location and validation outcome. A successful
download alone does not establish that every observation is correct.

### 2.1 Local storage and data-use restrictions

Downloaded market data is for local project research and analysis. It
must not be committed to or published in the public GitHub repository.

Technical access through a library does not, by itself, establish
permission for redistribution, sublicensing or every commercial use. Any
proposed use beyond local research must be assessed against the
applicable provider terms before proceeding.

## 3. Raw and adjusted prices

Price fields must be used according to their documented meaning. The
project must not mix raw and adjusted values without an explicit, tested
rationale.

-   **Raw OHLC prices** (`Open`, `High`, `Low`, `Close`) represent the
    provider's supplied daily price fields and are the starting point
    for defining plausible simulated execution prices.
-   **Adjusted close** (`Adj Close`), when supplied, reflects the
    provider's adjustment methodology for relevant corporate actions. It
    may be useful for historical return analysis, but it must not
    automatically be treated as an executable price.
-   **Adjusted OHLC values**, if generated by a library or
    transformation, must be distinguished from the provider's original
    fields. The exact transformation and its effect on the series must
    be documented.
-   Features and targets must use a consistent price convention. The
    chosen convention must be compatible with the forecast target and
    the intended interpretation of returns.
-   A feature computed using information that would not have been
    available at the prediction timestamp must not be used for that
    prediction.

The project must preserve an unchanged copy of acquired raw data. Any
cleaned, transformed or adjusted dataset must be stored separately, with
its transformation steps reproducible.

## 4. Dividends and stock splits

Dividends and stock splits affect the interpretation of historical
prices and simulated portfolio holdings. The project must identify the
treatment of these events before approving a backtest that depends on
total returns or historical share counts.

### 4.1 Dividends

The project must distinguish between:

1.  price returns, which measure price movement under the selected price
    convention; and
2.  total returns, which account for dividend distributions according to
    an explicit reinvestment or cash-accounting rule.

Dividend cash flows must not be added again if the return series already
incorporates them. If dividends are modelled as cash received by the
portfolio, the simulation must specify the relevant event date, amount,
eligibility convention, currency and treatment of cash. Any tax,
withholding or reinvestment assumptions must be explicit if they are
included.

Dividend fields supplied by a data provider must not automatically be
assumed to be fully reconciled or to represent cash received by a
particular historical position. Their date and amount conventions must
be checked before dividend-sensitive backtesting is approved.

### 4.2 Stock splits and other corporate actions

The simulation must account for stock splits when reconstructing share
quantities, position values or execution history. It must not apply an
additional split adjustment to a series that is already adjusted for the
same event.

Corporate-action records and price series should be checked for material
discontinuities around known events. A discontinuity is a diagnostic
signal, not proof of a data error: market movements and other events may
also explain price changes.

For `LLOY.L`, the project must record which corporate-action fields are
available from the selected source and what validation has actually been
performed. The historical audits previously conducted on AAPL, MSFT,
NVDA and TSLA are not evidence that Lloyds' observations or corporate
actions have been validated.

## 5. Volume and liquidity

Volume must be treated as a provider-supplied field whose adjustment
convention and limitations are documented. The project must not apply an
additional split adjustment unless the existing convention is
established.

`Close * Volume` may be used as a rough diagnostic proxy, but it must
not be described as exact traded turnover. Volume alone does not prove
that a simulated order could have been filled at the recorded price or
quantity.

If volume is used in features, liquidity filters, capacity assumptions
or execution modelling, the project must document the field,
transformation, availability timestamp and limitations. Any
execution-capacity assumptions must be conservative and must not be
inferred from volume without an explicit rule.

## 6. Simulated execution and transaction costs

Forecasting prices or returns does not by itself establish that a
strategy is profitable. Backtesting must model the timing and cost of
entering and exiting positions.

The target-generation convention currently intended for this project is
based on entry at the next session's open and exit at the close of the
target horizon. The implementation and the backtest must use compatible
timing. In particular, a signal calculated after close at session *t*
must not receive a fill at a price that was no longer available at that
decision time.

Before performance results are treated as decision evidence, the
backtest must define and apply, where relevant:

-   transaction commissions and fees;
-   bid--ask spread or a documented spread proxy;
-   slippage and market-impact assumptions appropriate to the strategy;
-   order timing and the price used for entry and exit;
-   position sizing, available cash and fractional-share assumptions;
-   treatment of dividends, splits and other corporate actions;
-   currency consistency between the asset, costs and portfolio;
-   constraints that prevent impossible trades or the use of unavailable
    prices.

Any simplified cost model must be clearly labelled as an assumption.
Results without realistic costs must not be presented as equivalent to
executable performance.

## 7. Data quality and temporal integrity

Every acquired dataset must pass documented quality checks before it is
used for modelling. At minimum, checks must cover:

-   expected columns and data types;
-   ticker identity, date range and daily frequency;
-   unique dates and chronological ordering;
-   missing or invalid dates and missing required price fields;
-   positive prices and non-negative volume;
-   OHLC consistency, where the supplied fields permit the check;
-   duplicate rows and unexplained gaps;
-   corporate-action fields and unusual price movements;
-   the actual last available trading session;
-   consistency between the source data, derived features and forecast
    targets.

Missing sessions must not automatically be filled as though the market
traded. Any imputation or exclusion must be justified, recorded and
applied without using future information.

Temporal validation must preserve chronology. Training, validation and
final test periods must be separated, with any necessary horizon-related
purging or embargo documented. All preprocessing, feature selection,
imputation, scaling and model selection must be fitted using training
information only, then applied to later periods without refitting on
future data.

Walk-forward evaluation is the required evaluation approach. Final test
observations must not be used to choose features, tune hyperparameters,
select models or revise the strategy. Overlapping forecast horizons and
repeated model comparisons must be considered when interpreting
performance.

## 8. Requirements for validating `LLOY.L`

The following items remain pending until supported by execution
evidence:

1.  Acquire the configured `LLOY.L` history through `yfinance`.
2.  Record the acquisition parameters, retrieval time and software
    version.
3.  Inspect the actual first and last available sessions and the number
    of observations.
4.  Run the documented data-quality checks and record any failures or
    exclusions.
5.  Inspect available corporate-action fields and validate
    representative events against reliable independent records where
    feasible.
6.  Document the price and volume conventions used by the selected data
    source and any transformations applied by the project.
7.  Verify that target generation, feature timestamps, walk-forward
    splits and simulated execution obey the same timing assumptions.
8.  Confirm that the processed dataset and modelling pipeline do not
    contain data leakage.
9.  Keep the original acquired data unchanged and preserve reproducible
    processing steps.

Until these checks have been run and their results recorded, the policy
must not claim that the `LLOY.L` history is fully validated. A test
passing against mocked data validates the tested code path; it does not
prove that a live download is complete or correct.

## 9. Asset selection and model-specific validation

`LLOY.L` is the initial development asset, not a permanent restriction
on user selection. When a user selects another eligible asset, the
system must validate its ticker, exchange, currency, available history,
data quality and corporate-action treatment before modelling.

Models must be trained and evaluated for the selected asset using
chronological validation. A model validated on one asset must not be
assumed to generalise to another asset. Model choice must be based on
documented out-of-sample evidence and appropriate baselines, not on a
single metric or forecasting accuracy alone.

The configured forecast horizons are 1, 5 and 10 trading sessions. The
target definition, entry/exit convention and model evaluation must
remain consistent for each horizon. Any change to these definitions must
be documented and tested.
